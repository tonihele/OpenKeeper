Trap animation behavior and timing
=================================
Checked against the user's original DKII.exe reference on 2026-11-20.
These are behavioral research notes, not extracted executable or asset data.
Comparison maps, screenshots, decompilation output and raw debugger samples
remain outside the repository.

Missing presentation
--------------------
TrapViewControl did not start the trap's authored mesh animation and always
requested animation stop. No game code selected the firing art resource.
The Fear Trap has distinct idle and active animated meshes; its idle-effect
ID is zero. Therefore periodic idle-effect emission is not the mechanism to
use for its movement. Other traps do have idle effects; those are separate
from the mesh animation work here and remain unimplemented.

Native animation transitions
----------------------------
The IDA catalogs were consulted before tracing the native trap routines.
The successful-shot path in sub_4A80E0 selects the firing resource. The trap
update in sub_4A84E0 returns the model to its idle resource once the active
animation has completed, unless trap flag 0x200 (LOOP_FIRE_ANIMATION) is set.
Blueprints are represented separately from the built trap's animated model.

Playback rate: finding and measurement
-------------------------------------
KmfModelLoader.handleAnim currently writes converted sample times as
(i + 1) / 30 seconds. Playing such a clip at speed 1 uses that conversion
rate, even when the referencing art resource requests a different rate.

The Fear Trap's authored idle is 60 frames at 15 fps: nominal duration 4 s.
Its active mesh is 60 frames at 45 fps: nominal duration 4/3 s. The initial
OK preview played both converted clips at speed 1, giving 2 s for each.
Consequently the idle was twice as fast as authored, while the active
animation was slower. This is a measured mismatch, not just an impression.

The native resource setup/advance path is sub_4B37D0, sub_4B41E0 and
sub_4B3C10. A bounded debugger trace of ordinary gameplay sampled the trap
update without changing counters, resources, health or game speed:
- The level ran at 4 game ticks per second.
- Idle normalized phase advanced by 256/4096 each tick and wrapped every
  16 ticks: an observed 4-second cycle, repeated across multiple cycles.
- Active normalized phase advanced by 768/4096 each tick, agreeing with
  the authored rate. The first wrap takes 6 ticks because native updates
  quantize the nominal 4/3-second duration to game ticks.
- In one transition the active resource was observed at ticks 14 through
  20 and idle again at tick 21. Native resource changes and completion
  flags have tick boundaries; nominal clip duration is not an exact
  measurement of the active resource's entire on-screen lifetime.

Current correction
------------------
The trap view derives the requested duration and instance playback rate:

  requestedDuration = resourceFrameCount / resourceFramesPerSecond
  instanceSpeed = loadedClipDuration / requestedDuration

This uses ArtResource.KEY_FRAMES, ArtResource.KEY_FPS and AnimClip.getLength.
It does not introduce a second hardcoded conversion FPS, per-trap speed table
or measured-duration constant. It also does not change shared clip data or
apply a new timing policy to every creature, door and effect. Missing or
nonpositive timing metadata keeps the existing clip rate.

Issue #1357 implements idle playback only. Visibility-only updates retain
its current phase; blueprints remain frozen and arming starts idle playback.
Activation playback and the separate Fear Trap eyes are tracked in #1359.
The private combined prototype used a successful-shot sequence to order
activation events; a sequence alone does not supply a shared phase clock.

Synchronization limits and possible follow-ups
---------------------------------------------
1. The correction matches the authored mesh playback rate with smooth render
   time. It does not reproduce native four-Hz phase stepping, completion-flag
   latency or tick-rounded resource-switch timing exactly. Keep those
   distinctions explicit when comparing active-animation lifetimes.
2. A shared animation timing helper could centralize metadata validation and
   clip-duration scaling, adopted by each entity type after its native rules
   are checked. Converter changes alone cannot safely choose one speed for
   a model referenced by multiple resources at different authored rates.
3. Publishing an authoritative shot start time with the event would let a
   late or delayed client seek to (gameTime - shotStartTime), rather than
   start its full active clip on receipt. Use synchronized game time so
   pauses, game-speed changes and late joining have defined behavior.
4. A common idle epoch/phase policy could align idle cycles where native
   behavior calls for it. Check native random-start behavior first; do not
   force every instance to move in lockstep merely for convenience.
5. If exact native parity is wanted, derive phase and completion from the
   level tick rate and normalized phase increment. Do not assume every
   level uses four ticks per second or hardcode the Fear Trap's durations.
6. Start/end animation segments and CLAMP versus WRAP need their own timing
   checks before a general policy is applied to all resources.

Validation
----------
Synthetic tests use generated scene graphs and clips without original game
assets. They cover idle looping, visibility
updates, blueprint arming, missing/invalid timing metadata and authored duration.
The duration regression deliberately uses a one-second synthetic clip and
independent authored metadata so a hidden assumption of 30-fps conversion
would fail it.

Separate finding
----------------
Without a Workshop, native trap/door blueprints alternate between normal
blueprint and highlight appearances on game-turn parity. This is tracked in
https://github.com/tonihele/OpenKeeper/issues/1356 and is outside the mesh
animation change. It was also observed historically in issue #234.

Follow-up: activation and Fear Trap eyes (#1359)
------------------------------------------------
The Fear shot's general effect supplies the eyes. In the comparison map this
is a line-of-sight shot, not a stationary shot. Its one-turn life can end in
the same game-loop iteration that creates it, before a client observes a
ShotViewState. The current implementation sends its independent general
effect through the existing generated-effect event and lifetime emitter.
Ordinary shot general effects detach on shot removal and finish naturally,
unless KILL_EFFECTS_WHEN_DEAD explicitly requests removal (sub_4AAF70).
PR #1343 supplies continuous shot-trail emission and is reused here.

Further native checks for the eyes:
- Effect generation height limits are signed shorts. Reading them unsigned
  put these elements far above the map.
- Element velocity has four extra fractional bits relative to positions;
  convert with the effect clock and that precision difference, not a
  trap-specific speed multiplier (sub_435F20 and sub_4476E0).
- CUBE_GEN expands its signed whirlpool rate by four bits before calling
  sub_438520 (caller sub_4386F0). Omitting the caller conversion makes the
  rotation too weak. Its impulse depends on squared distance from the
  generator and uses the native angular unit.
- Native horizontal wall sweeps reflect velocity even when elasticity is
  zero (sub_4472F0). Sprite particles now sweep tile boundaries too.
- Min/max scale define the random initial element scale. SHRINK/EXPAND
  interpolate towards that sample multiplied by scaleRatio, rather than
  between min/max scale. Verified in sub_435F20, sub_4363F0 and sub_4B4160.
  Ignoring the multiplier left the moving eyes too small to form the
  visible streams. Synthetic regression values test this distinction.

- The general effect's next-effect chain includes a launcher of moving,
  invisible generators. Those generators continuously leave stationary eye
  elements at successive emission points. Updating only the first general
  effect, or requiring art before moving a generator, leaves a central ring
  and loses the streams. Chained and newly generated effects now emit for
  their own authored lifetimes; existing particles retain their positions.
- Bounded native initializer samples confirmed that the moving eye's scale
  target is its starting scale multiplied by the authored ratio. The same
  samples confirmed the current drag conversion and neutral colour bytes;
  changing those to guessed values would not reproduce native behavior.

The user confirmed the outward streaks in the revised private preview.
This does not establish complete lighting or pixel-for-pixel parity with DKII.

The peaceful trap-targeting bypass is tracked separately in issue #1358.
A second private comparison map replaces the Knight with a level-1 Imp so
the active mesh can be observed over repeated shots without changing damage
or targeting rules in the implementation.
